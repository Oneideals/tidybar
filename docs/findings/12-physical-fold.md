# 隐藏区未在系统菜单栏隐藏 · 2026-09-09

用户反馈设置界面已把图标列入隐藏区，但实际菜单栏仍显示。已修正权限能力刷新、物理整理执行方式和分区验收；新版已构建并启动。**真实折叠效果尚未验收通过**：收尾时 Mac 仍锁屏，新构建的进程实际报告辅助功能未授予，处于收纳面板降级模式。

## 已确认的问题

| 问题 | 证据与修复 |
| --- | --- |
| 授权后仍沿用启动时的占位移动器 | 旧进程启动时无权限，随后读取器已能枚举图标，移动器却仍是占位实现。现在按机器和系统验证记录装配真实移动器，并在扫描时刷新权限能力；系统明确拒绝的拖拽能力仍保持降级。 |
| 主线程阻塞自己的状态项拖拽 | 原物理整理在主线程投递事件、休眠和轮询，同时拖动本进程的 `NSStatusItem`。新 `MenuBarArrangement` 用专用串行队列投递及验证，让主线程持续处理 AppKit 事件；布局、台账和界面更新仍在主线程。 |
| 同区排序失败也阻止整个隐藏区折叠 | 原路径要求全部 AX 项与保存顺序逐项一致。普通折叠现在稳定分组，保留区内现场顺序，只验证真实分界两侧是否正确；显式档案和位置调整继续使用保存顺序。 |
| 系统代理被误当成独立物理槽位 | [现场计划](../../.build/physical-fold-20260909-1/fold-plan.txt) 中 Control Center 代理帧完整包含 Surge，中心相同。物理规划、验收及控制器的落点计算共用代理过滤。代理是否随 Surge 移动没有现场确认；过滤依据是观测帧重合。 |
| 系统描述变化、解锁和换屏处理不一致 | 系统项文案变化不再触发受管分区变化。锁屏清除旧就绪状态；解锁、唤醒、显示器变化重新扫描并验收，防止同一批 ID 的位置已经变化却沿用旧结果。 |
| 后台输入与其它操作可能竞争 | 整理期间阻止分区、档案、规则、扫描落地及代点。正常退出和信号退出先取消、等待输入队列收尾，再释放应用资源。 |
| 取消、锁屏、换屏后仍可能继续当前拖拽 | 真实移动器逐步检查取消、锁屏及显示器几何变化，覆盖真实 Command 按下后、鼠标按下前的间隙；异常由当前工作队列按当前光标位置释放已按下的输入。 |
| 跨屏坐标混入同一排序序列 | 每次规划和验收要求所有受管图标及三控件属于同一屏幕菜单栏；跨屏或离屏的待整理项目明确拒绝，其他屏幕的系统观测不参与排序。没有声称实现独立的多屏布局。 |
| 系统时间校正可扩大等待 | 冷却和落位截止改用单调时钟，冷却另有上限。 |
| 可选真实 Command 模式键码错误 | `0x38` 是 Shift，已改用 `kVK_Command`；探针收尾复用同一投递器。默认仍使用鼠标事件的 Command flags，不额外按真实 Command 键。 |

重启旧包后的 [启动日志](../../.build/physical-fold-20260909-1/app.stderr.log) 已确认“辅助功能权限 = 已授予｜模式 = 完整接管”，但当时整理仍失败。因此本次问题不能只归因于用户没有授权。

## 回归与构建

- 完整 Debug 和 Release 各 **268 条用例、39 个套件通过**。
- 新 `MenuBarArrangement` 套件有 11 条用例，包括主线程事件消费、取消后排空、忙碌门禁、代理槽位、锁屏恢复、权限升级、同高及异高副屏拒绝，以及真实 Command / flags 模式中的取消和换屏。
- 代理槽位回归先得到错误落点 `642`，修复后得到真实邻居右缘 `614`。跨屏回归修复前发出移动，修复后零移动且明确失败。
- 在途取消/换屏回归修复前会继续发 `mouseDragged`；真实 Command 分支还会多发 `mouseDown`。最终四组均在中断后停止新增输入，并释放已按下的键或鼠标。
- 全量测试还暴露旧测试夹具的信号量析构错误。`invalidatedScanCannotOverwriteManualChanges` 将初值为 1 的信号量作为一次性令牌消费却不归还，异步主循环释放闭包时触发 libdispatch 断言。改为初值 0、显式投入一次令牌后，全量测试不再崩溃。
- Release 全目标构建、打包及严格签名校验通过，包体积 **2008 KiB**。
- Standards 与 Spec 的限定只读复核发现项已处理；该复核不替代真实菜单栏验收。

## 现场证据的边界

调查后半段发现 Mac 已锁屏。此时 AX 仍可读、光标位置也可能变化，不能由此认定系统会正常处理拖拽。该阶段的 `leading-drop-*`、`control-*` 等实验记录只能保留为未定结果，不能用于选择拖拽落点或 Command 释放语义。

本轮没有根据这些锁屏实验修改 `MenuBarDropTarget` 的中心/右缘计算，也没有改变鼠标抬起时的 flags。`.build/physical-fold-20260909-1/fold-probe` 链接的是旧代码，不具备新增锁屏保护，不应在锁屏时重跑其移动模式。

最终新版进程为 **PID 16610**；[实际启动日志](../../.build/physical-fold-20260909-1/app-latest.stderr.log) 报告辅助功能未授予、收纳面板降级，初始物理内存占用 12.1 MB。该权限读数来自新进程，旧系统设置条目的勾选状态不能代替它。

更换代码前后的已提交布局文件与最近的 `before-code-upgrade` 备份逐字节一致：**隐藏 30 项、显示 4 项**，SHA-256 为 `01e6f4790bc05d1938dfde94adf5d95f6b38dff951645b778773a7ef0a8dbac6`。这是比最初 35 项备份更新的状态，未用旧备份覆盖它，也未把内存界面计数当作磁盘文件计数。

## 待继续的现场验收

1. 用户解锁 Mac，并为当前 `dist/TidyBar.app` 处理辅助功能授权；观察新进程是否转为完整接管，必要时重启后确认。
2. 在未改用户分区的前提下执行整理，同时读回分隔符和图标坐标，确认隐藏区图标实际离开可见菜单栏、常驻图标仍可见。
3. 验证展开/折叠、自动收起、始终隐藏、演示进入/退出、锁屏解锁及退出时输入释放。
4. 多显示器场景验证正确同屏操作或明确拒绝；不能把拒绝跨屏拖拽写成已支持独立多屏布局。
