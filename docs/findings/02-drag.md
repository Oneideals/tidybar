# M0 验证项 2 结论：⌘ 拖拽与事件哨兵

日期：2026-09-04 ｜ macOS 26.6.2 (25G83) ｜ 实验对象：**只有我们自己造的 fixture 图标**（`local.tidybar.fixture`，见 `Sources/TidyBarFixture`），全程未触碰用户任何真实 App 的图标。

复现：
```bash
./scripts/build-fixture-app.sh && open dist/TidyBarFixture.app --args 4
swift run tidybar-drag-tune --runs 6        # 落点假设验证
swift run tidybar-drag-probe --repeat 100 --destructive   # 闸门 + 中止路径
```

## 结论

**可行，且闸门已达标**：连续 **100/100 成功**，零卡键卡钮、零身份丢失、`consecutiveSuccesses = 102`、单次 p50 ≈ 400ms。中止路径经真机 + 离线双重验证。但过程中被真机数据推翻了三条我自己先入为主的假设，其中两条若没做实验就会变成线上事故。

## 三条被推翻的假设

### 1. "失败是时序问题" —— 错，参数扫描直接否掉

初测 50% 成功，我判断"缺了按下后的持住时间"。于是扫 `hold ∈ {0, 0.07, 0.16}s × stepCount ∈ {6,12,24}`：

| hold | steps | 结果 |
| --- | --- | --- |
| 0 / 0.07 / 0.16 | 6 / 12 / 24 | **对成功率零影响** |
| 任意 | 任意 | dist=40pt → 0/27；dist=100pt → 成功 |

只有**距离**这一个变量起作用。我的"持住时间"假设被数据否决（改动方向还一度让成功率掉到 15%，纯属噪声）。

### 2. 真正的决定因素：**落点必须踩在邻居图标的槽位上**

针对性验证（`tidybar-drag-tune --runs 6`）：

| 落点 | 结果 | 预期 |
| --- | --- | --- |
| A 往后插到邻居右缘 | **4/4 重排** | 会 |
| B 往前插到邻居中心 | **4/4 重排** | 会 |
| C 往左拖 100pt 进空隙 | **0/4 重排** | 不会 |

**macOS 对落到空隙里的 ⌘ 拖拽是静默忽略**——不报错、不移动，工具会以为成功。这解释了最初 50%/15% 里所有失败样本（我用的是"往左右 N 像素"）。

已按事实重构：`MenuBarDropTarget` 从当前图标顺序推导目标 X（往前插取目标邻居中心，往后插取其右缘+2），无合法落点就返回 nil；"顺序是否改变"作为成功判据（而不是"坐标变了"，弹回原位必须算失败）。7 条离线用例锁死这套推导。

**产品含义**：`LayoutEngine.targetProvider` 只能用 `MenuBarDropTarget`，任何"往左 N pt"的实现都会变成静默失效——这条也直接影响 P1 的分隔符/分组设计。

### 3. ⌘ 的实现方式：必需的和有害的是同一件事

三步判别：

1. 鼠标事件**不带** `maskCommand`（只发真实 ⌘ keyDown）→ **0/12 完全不重排** ⇒ 让菜单栏认定 ⌘ 拖拽的是**鼠标事件自带的 flags**，按键事件不能替代它。
2. 只发 flags、不发任何按键 → 依然 100% 重排，但 ⌘ 读数仍报按下。
3. 用一个**从未投递事件的独立进程**读 `CGEventSource.flagsState(.combinedSessionState)` → **⌘ = true**。

⇒ 我们贴在鼠标事件上的 flags **会改写全局 session 修饰键状态**；若以带 flags 的事件收尾，用户之后的普通点击就会变成 ⌘ 点击（右键/多选级别的怪事，且极难归因）。

修复只需一条：**抬起事件必须不带 flags**。加上之后独立进程读数回落为 `false`，成功率仍 100%，卡键副作用 0。产品默认同时改为**不投递真实 ⌘ 按键**（既然它非必需，就少一个能把修饰键卡住的源头）。

这条是本次最值钱的发现：它不会以"崩溃"形式暴露，只会以"用户偶尔觉得鼠标行为怪了"的形式存在。

## 中止路径（该停手时是否真停手）

| 场景 | 真机 | 离线断言 |
| --- | --- | --- |
| 用户按住鼠标时抢操作 | ✓ 让位（一个事件都不发） | ✓ `yieldsWhenUserHoldsMouseButton` |
| 目标图标消失 | ✓ 明确 `itemVanished` | ✓ |
| 未确认 OS 上 | ✓ 一律 `unsupportedOS`，绝不动图标 | ✓ |
| 光标放置后被抢走 | 未能稳定构造（warp 与读数毫秒级竞态）→ **不计通过** | ✓ `releasesCommandWhenCursorDriftsMidDrag`（含"中止也必须抬 ⌘/鼠标键"） |
| 系统拒绝投递 | — | ✓ 仍走完收尾，不继续拖 |

另有 10 条拖拽事件纪律用例（`DragEventDisciplineTests`）：中止时零事件、⌘ 只按一次只抬一次、事件顺序 warp→⌘→down→drag×N→up→⌘↑、失败路径必须收尾、坐标换算符号锁死。回归总数 **124 条全绿**。

## 遗留与下一步

- **闸门仍未打开**：100 次绿是在这台机器、这个系统版本、fixture 图标上取得的。产品侧 `isConfirmedSupportedOS` 保持 `false`；开放完整接管前需在**用户真实图标**上（获得许可后）与**其他 macOS 版本/非刘海机型**上各自复跑。
- **p50 ≈ 400ms/次** 里有 ~150ms 是 mover 内部的图标表读取；已加定向单进程读取 `discoverItems(owning:)`（毫秒级），下一步把 mover 全面切到定向读取，可压到 ~250ms。
- ⌘ 键状态检测在真机上不可靠（受 session flags 影响），产品里不能把它当用户按住的唯一依据。
- 尚未验证：Space 切换/全屏 App、多显示器（图标在主屏外）、以及拖拽被系统的"自动隐藏菜单栏图标"策略干扰的情况。
