# M1 第一步：点击转发（面板/搜索里的点击打到真实图标上）

日期：2026-09-05 ｜ macOS 26.6.2 ｜ 29 个进程 66 个 AX 子项在栏
复现：`swift run tidybar-self-drag --press-census` ｜ `swift run tidybar-self-drag --activate <bundleID>`

## 为什么先做这个

收纳面板的验收标准（报告 A3）是"面板里点图标 = 点真实菜单栏图标"。这条能力不做，
面板就只是个展示窗；它也是 A8 图标搜索"键入名称定位并激活"的前置。
而且它**不依赖接管闸门**——所以能在真实图标不能搬动的现在，就把面板变成可用的。

## 三个实测结论

**1. 用 `AXPress`，不用合成鼠标事件。**
品类通行做法是往图标坐标投一对 mouseDown/mouseUp，但那等于自己造一次"幽灵点击"的风险面：
坐标漂一点就点到邻居，还得处理"按住态残留"。AX 动作直接打在元素上，不经光标，
和 ⌘ 拖拽那套合成事件完全分开。代价是"能读到不等于能点到"，必须先量覆盖率。

**2. 可点性普查（只读，绝不真点）：66 个子项里 65 个接受 `AXPress`，覆盖率 98%。**
29 个进程只有 BetterDisplay 是 1/2（其中一项是自绘、不给 AXPress）。
这条数字直接决定 A3 能不能承诺"面板里都能点"——上线前的口径应当是 98% 而不是 100%，
并对点不动的那一类给出人话提示。普查故意**只读动作列表**：真去点会把每个 App 的菜单都弹一遍。

**3. `kAXErrorCannotComplete(-25204)` 不是失败。**
第一次对 fixture 图标 AXPress 时系统返回 -25204，但 fixture 的事件日志里确实多了
`menu-open FX3`——**菜单打开了**。原因是带菜单的状态项在 AXPress 后立刻进入模态跟踪循环，
来不及回执。据此把结果分成 `pressed` 与 `pressedUnconfirmed(code:)`，两者都算"点到了"
（`countsAsPressed`）。如果照错误码直接报"系统拒绝了这个点击"，用户会以为没点上而再点一次，
体验上就变成了"工具会双击"。这一条是 fixture 侧日志与探针返回值对照出来的，
没有事件日志就只能靠猜——所以先给实验品加可观测点，再谈验证。

## 边界与真相当面

- **未接通时必须说不通的原因**。`SystemServices.activator` 允许为 nil（骨架装配、离线测试），
  此时 `activate` 返回 `actionUnsupported` 并把原因写进诊断日志与面板提示行，
  而不是静默返回"成功"。`UnverifiedMenuBarActivator` 同理。
- **代点不是布局变更**：不写 journal、不留 pending（有用例钉住）。失败也不该留下任何半成品。
- **始终隐藏区的项**：先呼出再代点，否则用户点了看不到任何反应。
- 面板新增一行反馈文字（`TidyBarPanelView.notice`），只在代点失败时出现；放不下就不画，
  宁可少一行字也不压住图标。
