# M0 追加：真实菜单栏闸门（我方图标 × 用户真实邻居）

日期：2026-09-05 ｜ macOS 26.6.2 ｜ 35 个图标在栏（含 28 个第三方 + 系统项）
复现：`./scripts/build-app.sh && open dist/TidyBar.app` 后 `swift run tidybar-self-drag --repeat 20`

## 为什么要单独跑这一轮

之前所有绿灯（100/100、`--via-engine` 30/30）都只在**自造 fixture 图标**上取得，而 fixture 的邻居也是
fixture——从没验证过"落点在真实的、别的 App 的图标之间"是什么行为。这一轮把被拖对象换成 TidyBar
自己的 ☰ 图标（同样是带 bundle id 的真实 App 图标），邻居全是用户真实图标：落点、槽位、系统重排路径
全是真的，但不会由我们主动搬走用户任何一个图标（每一轮成对反做，结束核对全局顺序复原）。

## 抓到并修掉一个只在真实环境下暴露的 bug

**现象**：全新进程里的**第一次**拖拽稳定失败 `noVisibleEffect`，第二次起就成功——反复可复现。
在 fixture（4 个图标）上从来不复现。

**根因**：`LayoutEngine.performDrag` 在抬起鼠标键后**只读一次帧**就判定"系统没接受这次拖拽"。
菜单栏重排是异步的，35 个图标的真实菜单栏落位比 4 个 fixture 图标慢，第一次扫描还叠了冷启动开销，
于是读到的是旧位置 → 误判失败 → 回滚。**是复核太急，不是拖拽没成**。

**修法**：结果复核改成有界轮询（默认 600ms 窗口 / 60ms 步进，`verificationWindow`、
`verificationInterval` 可在初始化时调），一旦读到真的动了立刻返回——所以**成功路径不付额外延迟**，
只有慢或真失败才会用尽窗口；离线测试把窗口压到 0 保持秒级。

**为什么这个 bug 值得单独记一笔**：它同时说明"结果复核"这个机制是对的——它没有把一次没落定的拖拽
当成成功写进布局，而是回滚重试；但也说明**判据本身不能急**。只在 fixture 上做验证，永远看不到这条。

## 修完的实测

| 项目 | 结果 |
| --- | --- |
| 轮次 | 8 + 20 + 20 = 48 轮（双向往返 = 96 次真实拖拽） |
| 成功率 | 96/96，第一轮起就成功 |
| 单次拖拽 | p50 359~372ms ｜ p95 373~424ms（走 `LayoutEngine.apply`，含 journal + 复核轮询） |
| ⌘ / 鼠标键残留 | 0 次 |
| 图标身份 | 0 次"拖完找不到同一个 id"（35 项全局顺序里按 id 追踪） |
| 全局顺序复原 | 每轮结束都与初始完全一致（35 项逐项比对） |

## 还没被这一轮覆盖的

- **被拖对象仍是我们自己的图标**：用户的某个具体 App 的图标被拖走再放回，这条路径没跑过。
  开放完整接管前，如果要按"用户真实图标"字面判据补，需要单独授权并指定目标 App。
- 带 `NSMenu` 的图标（我们的 ☰ 就带菜单）与非菜单图标是否行为一致，没有做对照。
- 非刘海机型、macOS 14/15、多显示器负原点场景仍未覆盖。
- 真人同时使用鼠标会让哨兵让位或让拖拽被系统吞掉——跑闸门期间必须不碰鼠标键盘，
  这不是可以靠"多跑几次"绕过去的噪声。
