# M1 第二步：图标真实缩略图（抓图 + 缓存 + 回退）

日期：2026-09-05 ｜ macOS 26.6.2 ｜ 36 图标在栏，主屏 2x
复现：`swift run tidybar-self-drag --capture local.tidybar.fixture`（加 `--causal` 跑因果验证）

## 一处被明确否决的做法

第一版是「抓整块屏幕 → 本地裁目标区域」，理由是裁剪属性在副屏/混合缩放下语义不稳。**这个取舍被否掉了**：
为了自证而去抓一次用户的整个桌面，本身就是新的隐私代价，哪怕只在内存里停留一瞬。
现在改成 `sourceRect` 只抓目标那一小块，全工程不再有任何整屏抓取路径（探针里那个"整屏对照"也一并删掉）。

## 四条已知答案判据（全部真机通过）

尺寸对不代表内容对——整屏缩放到 92×48 也一样是 92×48。所以判据不能依赖猜测：

| 判据 | 实测 |
| --- | --- |
| 输出尺寸 = 目标区域 × 缩放 | ✓ 期望 92x48px，实际 92x48px |
| 同区域连抓两次逐像素相同（确定性） | ✓ 指纹 300666826 = 300666826 |
| 不同图标抓出不同内容（坐标参与裁剪） | ✓ 300666826 ≠ 1554239589 |
| **因果**：把该图标挪走一格后抓同一位置，内容必须变 | ✓ 300666826 → 331660946，之后已挪回原位 |

前三条只能证明"坐标参与裁剪"，证明不了"坐标一分不差"；第四条让现场内容真的变化，
才把"抓对了这一格"与"抓了某块固定区域"区分开。因果验证只在自造 fixture 图标上做，跑完复原。

**中途有一条判据本身是错的**：最初对照用"往左 400pt 的空白处方差应接近 0"。
但 36 个图标挤在约 1400pt 的带上、平均间隔才 40pt——往左 400pt 是**另一个图标**，不是空白。
于是那次 `✗ 目标处 861 vs 空白处 1923` 报的是判据错了，不是抓图错了。
教训：**对照实验的假设也要被验证**，否则会把自己的设计缺陷记到被测系统头上。

## 缓存语义（12 条离线用例钉住）

- 缓存键只有 id 不够：**位置一变，旧位图立刻失效**，否则面板显示的是它旧位置的截图（"缩略图串位"，比没图更糟）。
- 心跳每 0.25s 重绘一次，所以"要不要抓"必须问缓存：位置没变就不抓（`repeatedScanWithoutMovementNeedsNoCapture`），
  控制器另有 `inFlight` 闸门防同一批图标被重复送去做屏幕录制。
- 字节按**像素**算不按点算：按点算会在 Retina 上低估一半，20MB 预算形同虚设。
- 单张超上限直接不入缓存，不挤掉别人；App 退出后用 `retain(alive:)` 清掉。
- 未授权是常态路径：占位实现永远返回 `notAuthorized`，面板回退首字母占位，功能不塌（真机已验证该分支）。

## 已知不足

- `sourceRect` 在副屏负原点、混合缩放下的行为未验证（本机只有一块屏）。
- 一次显示 20 个图标会并发 20 个抓图请求，高负载下的排队与耗时没测。
- 抓图必须在主线程发起（NSScreen 线程限制），若未来把扫描挪到后台需同步改这里的取值方式。
