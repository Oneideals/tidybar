# M1 里程碑：用户真实 App 图标的拖拽闸门（100 轮全绿）

日期：2026-09-05 ｜ macOS 26.6.2 ｜ 目标：**QuitAll**（`com.quitallapp.quitall-paddle`，1 个图标，用户指定）
复现：`.build/debug/tidybar-self-drag --bundle com.quitallapp.quitall-paddle --repeat 100`

## 为什么这次才敢说"真实图标"

此前的所有绿灯都只在自造 fixture 图标上取得（fixture 的邻居也是 fixture）。后来加的那轮用我们自己的
☰ 图标当被拖对象、邻居是用户真实图标——落点真实了，但**被拖的仍然不是用户的资产**。
这条判据（拖动用户某个 App 的图标再放回）一直空着，今天由用户点名 QuitAll 补上。

## 实测

| 项目 | 结果 |
| --- | --- |
| 轮次 | 100 轮，每轮"挪走一格 + 挪回原位"＝ **200 次真实拖拽** |
| 成功率 | 200/200，无一轮失败 |
| 单次耗时 | p50 391ms ｜ p95 419ms（走 `LayoutEngine.apply`，含 journal 写盘 + 结果复核轮询） |
| ⌘ / 鼠标键残留 | 0 次 |
| 图标身份 | 0 次"拖完找不到同一个 id" |
| 全局顺序 | 收尾与初始**逐项一致**（32 项） |

先跑了一次 5 轮小样确认安全再放大到 100，中途不碰鼠标键盘（真人动鼠标会让哨兵正常让位、拖拽被系统吞掉，
那属于测不出东西的假失败）。

## 顺手抓回一个"能力被静默删掉"的事故

`--repeat 5` 第一次跑时**没有任何输出、退出码还是 0**。根因不是拖拽，而是我早先用脚本删文件尾部代码时
把整个主闸门流程连带截掉了——探针只剩 `--activate/--capture/--press-census/--search-ui` 几个前置模式，
主循环整段消失，而 Swift 顶层代码顺序执行到文件尾自然返回 0。

这是同一个老毛病的第三种形态：直连组件绕过主路径、fixture 环境不代表真实菜单栏、**这次是"被测对象本身被改坏了却没人报警"**。
已恢复该段（`git show 4cb1164` 取回），并记下两条守则：
1. 删代码的脚本必须以"删掉的行数"为断言对象，不能用 `rfind` 猜尾巴；
2. 任何"退出码 0 但零输出"都当失败处理——跑测器至少要在开头打印环境头，缺头即失败。
