# M1 里程碑：用户真实 App 图标的拖拽闸门（100 轮全绿）

日期：2026-09-05 ｜ macOS 26.6.2 ｜ 目标：**QuitAll**（`com.quitallapp.quitall-paddle`，1 个图标，用户指定）
复现：`.build/debug/tidybar-self-drag --bundle com.quitallapp.quitall-paddle --repeat 100`

## 为什么这次才敢说"真实图标"

此前的所有绿灯都只在自造 fixture 图标上取得（fixture 的邻居也是 fixture）。后来加的那轮用我们自己的
☰ 图标当被拖对象、邻居是用户真实图标——落点真实了，但**被拖的仍然不是用户的资产**。
这条判据（拖动用户某个 App 的图标再放回）一直空着，今天由用户点名 QuitAll 补上。

那属于测不出东西的假失败）。

## 顺手抓回一个"能力被静默删掉"的事故

`--repeat 5` 第一次跑时**没有任何输出、退出码还是 0**。根因不是拖拽，而是我早先用脚本删文件尾部代码时
把整个主闸门流程连带截掉了——探针只剩 `--activate/--capture/--press-census/--search-ui` 几个前置模式，
主循环整段消失，而 Swift 顶层代码顺序执行到文件尾自然返回 0。

这是同一个老毛病的第三种形态：直连组件绕过主路径、fixture 环境不代表真实菜单栏、**这次是"被测对象本身被改坏了却没人报警"**。
已恢复该段（`git show 4cb1164` 取回），并记下两条守则：
1. 删代码的脚本必须以"删掉的行数"为断言对象，不能用 `rfind` 猜尾巴；
2. 任何"退出码 0 但零输出"都当失败处理——跑测器至少要在开头打印环境头，缺头即失败。

## 追加：判据修好之后，第 100 轮真的过了（并写了确认记录）

第一次 100 轮被判据自己误杀：`snapshot()` 拿 **id** 比对顺序，而 id 含标题；微信那段时间把未读数
写进了标题，于是 `com.tencent.xinwechat.1 → …#item0` 被算成"没复原"。

改法是把两件事拆开：

| 维度 | 依据 | 语义 |
| --- | --- | --- |
| 是否放回原位 | **位置指纹** `归属进程[进程内序号]` | 我们挪动时它会变、放回后变回来；别人改标题时它不动 ⇒ 敏感于我们的失误，免疫于第三方改名 |
| 标题漂移 | 按位置键配对前后两帧，比对标题 | **只报告不判失败**（那是别人的行为），但漂移过的进程要被点名：它们的标题不能当身份，设置界面须把这类图标标成"按位置认领" |

复跑：**100 轮 / 200 次拖拽全绿**，p50 385ms / p95 415ms，位置逐项复原，零卡键残留、零身份丢失、
全程无第三方标题漂移。确认记录已写入：

```
{"confirmations":[{"confirmedAt":"…","machineID":"hw:8D3DE04A-…","osVersion":"26.6.2","rounds":100}]}
```

下次启动即 `模式 = 完整接管`（本机本版本命中名单）；同一份代码在别的机器或 26.6.1/26.5.x 上仍是
收纳面板降级模式，因为名单里没有它们的记录。

## 还没解决的那一半（第 2 项只做了一半，说清楚）

- **已解决**：漂移能被观测、被报告、被点名（`detectTitleDrift` / `volatileTitleOwners`，4 条用例）。
- **未解决**：标题型 id 一旦漂移，**已经保存的分区归属会错位**——用户把"微信"收进隐藏区，微信改标题后
  工具认不出同一项，图标会被当成新出现的项按默认策略处理。正确修法需要三件配套：
  1. 对漂移过的进程放弃标题身份，退回 (进程, 序号) 并显式标注不确定性；
  2. 已存归属的迁移策略（旧 id → 新 id 的映射，且必须可回退）；
  3. 与 P1-C 的设置迁移一起做，避免"加字段静默重置老用户设置"那类连带伤害。
  现在没做，是因为只有"漂移能观测"这一步的证据，样本量还不足以定身份策略（本机窗口内只有微信一处）。
