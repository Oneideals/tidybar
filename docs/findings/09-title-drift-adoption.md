# 微信改标题之后，收纳配置不再丢（标题漂移认领）

日期：2026-09-05 ｜ macOS 26.6.2 ｜ 触发样本：`com.tencent.xinwechat`（未读数写进 AXTitle）

## 现象与根因

id 由 `归属进程 + 标题` 组成（findings/01：88% 图标没有可读标题，剩下的有）。
微信把未读数写进标题，标题一变 id 就变，于是：

- 用户把"微信"收进隐藏区 → 微信来消息 → id 变了 → 布局里查不到 → 按"新出现的图标"处理 ⇒ **收起来的自己又冒出来**；
- 拖拽闸门的复原比对也被它绊过一次（第 19 位差异，见 findings/08）。

## 改法：只在"一个进程只有一个图标"时认领，并且把配置改名跟过去

`MenuBarLayout.soleZone(forOwner:)`：该进程在本工具布局里**只有一条**配置时，返回它所在分区。
`LayoutEngine.fold(items:)`（控制器与 `synchronize` 都改走这条）在遇到"没见过的新 id"时：

1. 要求 `ownerItemCount == 1` **且**该进程只有一条已存配置；
2. 满足则把那条配置 `rename` 到新 id（保持所在分区与左右顺序）——不改名只是权宜，下次扫描还得再猜；
3. 不满足（同进程多图标）**一律不猜**，按默认分区新建。

为什么宁可不猜：多图标进程里"就近认领"会把兄弟图标的配置偷走，用户看到的是
"另一个图标莫名其妙被藏了"——比配置丢一次更难查、也更伤信任。

## 验证

- 离线 4 条用例（`TitleDriftAdoption`）：改标题后归属跟着走且旧 id 迁净；同进程两图标时新项落默认区、旧配置原地不动；`soleZone` 要求"恰好一条"；`rename` 保持顺序。回归 **175 条全绿**。
- 漂移可观测性在上一轮已就位（`detectTitleDrift` / `volatileTitleOwners`，闸门里只报告不判失败）。
## 真机因果验证（已做完，正反两向）

fixture 加了受控漂移源：`TIDYBAR_MUTATE_TITLE=1` 时最后一个图标每 2.5s 自改标题
（`MX` ↔ `MX (n)`），于是"漂移 → 认领 → 配置不丢"成为可重复实验，而不是守著微信等它来消息。

| 实验 | 结果 |
| --- | --- |
| 单图标进程（`--args 1`）+ `--drift-e2e` | 漂移 1 处被观测；新 id `…mx (3)` 落到**隐藏区**，旧 id 迁净 ⇒ 配置跟随 |
| 三图标进程（`--args 3`）+ `--expect-no-adopt` | 漂移 2 处被观测；新 id **不被认领**，旧配置原地保留 ⇒ 不猜的设计成立 |

两次踩坑都值得记：
1. 第一版 fixture 带 4 个图标，被拖的图标属于多图标进程 ⇒ 按设计本就不该认领，
   却把它当成"认领失败"来查——**实验对象不满足被测前提**；
2. 再一版固定睡 6 秒，正好落在标题复位的那一帧，漂移记数为 0，看起来像"没有漂移"。
   改成**轮询到标题真的变了为止**之后才有因果。**"没观测到"不等于"没发生"**，
   这类采样错误会直接伪造出阴性结果。

## 仍未解决

- 多图标 App 的标题漂移：现在只是不猜（已由反向对照证实），配置仍会丢。真要解决需要身份降级 + 可回退迁移（P1-C）。
- 漂移计数目前是进程内观测，没有跨启动累计，因此"这个进程的标题不可信"不能持久化到下次启动。
