# 设计：跨启动身份台账（让标题漂移不再丢配置）

状态：**已实现**（提交 acdb0d0 起）；真机跨启动两段式验证通过（--ledger-seed / --ledger-verify，
改名后新 id 仍在隐藏区、旧 id 迁净）。升级迁移（§4）与多对多保全仍在 P1-C 名下
前置结论：findings/01（88% 图标无标题）、findings/08（位置指纹判等）、findings/09（漂移认领的真机正反例）

## 1. 问题不是"改名"，是"我们把用户的选择存在了别人的可变字段上"

现在的身份是 `归属进程 + 归一化标题`（无标题时退回 `#itemN`）。用户的分区归属就挂在这个 id 上。
于是微信把未读数写进标题的那一刻，**用户的选择被存进了一个我们并不拥有的字段里**。

当前已有的补救只有一条：同一进程内「唯一没配上的旧 id」+「唯一的新 id」⇒ 判定为改名并改名跟随
（findings/09 已真机验证正反两向）。它覆盖了"一个进程里只有一个图标改名"这种最常见情形，但：

- 一次出现两个新 id（两个图标同时改名、或改名与增删同时发生）→ 配对不唯一 → 配置丢；
- 重启工具后，旧的待认领 id 已经不在布局里了 → 连"唯一旧 id"这个线索都没了。

第二点才是"跨启动"的要害：**线索必须活过一次进程生命周期**，否则每次重启都把漂移当新图标。

## 2. 核心决定：用户的分配拥有自己的身份

不再让"用户的选择"寄生于任何 AX 派生 id。引入一个我们自己发的、永不复用的键：

```
assignmentKey = "a-" + UUID            // 由工具生成，只在台账与布局里出现
```

台账（`identity-ledger.json`）把 `assignmentKey` 与**它历史上观测到的所有 AX 身份**绑在一起：

```jsonc
{
  "version": 1,
  "entries": [{
    "assignmentKey": "a-6f1c…",
    "ownerBundleID": "com.tencent.xinwechat",
    "identitySource": "axTitle",
    "aliases": ["com.tencent.xinwechat.微信", "com.tencent.xinwechat.微信 (3)"],
    "ordinal": 0,
    "ownerItemCount": 1,
    "zone": "hidden",
    "pinnedBy": "user",          // user=用户亲手分配 / inferred=按规则推断
    "driftCount": 1,
    "lastSeenAt": "2026-09-05T06:21:50Z"
  }]
}
```

要点：
- **布局只存 `assignmentKey`**，不再直接存 AX id。id 是易变的观测值，key 是不变的决定。
- `pinnedBy` 与 `driftCount` 让设置界面能如实说"这一项是按位置认领的，可能失准"，而不是假装一切确定。
- 上限：每进程别名最多 8 条（先进先出）；条目按 `lastSeenAt` 清理。台账是小 JSON，不进 `ImageCache`，也不参与热路径。

## 3. 匹配规则：按优先级取"唯一命中"，拿不准就什么都不做

对每个现场图标依次尝试，**任何一步出现多解即停止并记为歧义**：

1. **别名精确命中**（常见、零成本）；
2. **同进程 + 同序号 + 进程图标总数未变**（序号只有在总数不变时才是同一位置，总数变了就换主人了——这条判据来自 findings/08 的教训）；
3. **同进程 + 标题前缀/子序列包含**（`微信 (3)` 包含 `微信`），且候选唯一；
4. 都不成立 ⇒ 新建 `assignmentKey`、按 A7 默认策略归位、把这次歧义写进诊断日志。

设计红线（都是这轮学来的）：

- **宁丢不错接**：把一个图标的设置安到兄弟图标头上，比配置丢一次更难查、更伤信任（findings/09 的反例就是为它写的）；
- **不做任何周期性工作**：台账只在扫描后同步匹配一次，不挂表、不轮询（空闲 CPU 预算刚立过这条契约）；
- **不塞进 `AppSettings`**：它是合成 `Codable`，加字段会让老用户已存设置解码失败并被静默重置。台账独立成文件，且解码失败一律按"无台账"处理（保守），绝不猜成"已迁移"。

## 4. 从现状升上来的路

1. 首启检测到有 `layout.committed.json` 但没有台账 → 为每个已存 id 生成 `assignmentKey`，把那个 id 作为**第一个别名**写进台账（`pinnedBy: user`）；旧布局文件保留只读备份 `layout.committed.pre-ledger.json`，可回退；
2. 升级后第一次扫描只做匹配不改动布局，把 `matched / ambiguous / orphan` 三类计数打进日志；
3. 只有第 2 步 `ambiguous == 0` 才启用"改名跟随写回"；有歧义时保持原样并提示用户复核——**升级不该制造新的错位**。

## 5. 验收怎么做（不再靠"看起来对"）

离线：纯函数 `IdentityLedger.resolve(observed:entries:)`，表驱动用例覆盖
精确别名／序号命中+总数未变／序号命中但总数变了（须拒绝）／前缀包含候选唯一／1↔2 与 2↔2 歧义／
重启后凭别名恢复（序列化往返）／别名上限与清理／解码失败退回无台账。

真机（复用 findings/09 的受控漂移源，避免"守著微信等它来消息"）：
- `TIDYBAR_MUTATE_TITLE=1`：单图标改名，**kill -9 后重启**再验——这才叫跨启动；
- `=2`：两个图标同时改名，断言两者都不被错接（原行为是丢配置，有台账后应经别名规则 3 各自对上，若仍歧义则如实报 `ambiguous>0`）；
- 新增 `=3`：改名 + 同时增/删一个图标（打破"总数未变"前提），断言规则 2 拒绝、规则 3 只在唯一时接管。

判定口径：漂移后配置存活率、以及**错接数为 0**（错接为 0 是硬条件，存活率允许因保守而低于 100%）。

## 6. 明确不做

- 不做"图标截图感知哈希"这类指纹匹配：抓的是别人的桌面像素，隐私代价与收益不成比例（同 findings/07 否决整屏抓取的理由）；
- 不在启动时同步全量扫台账 + 全量枚举（会击穿启动预算，findings/04 刚为此把冷启动从 2.8s 压到 0.5~1.0s）；
- 不引入第三方持久化依赖（工程零依赖是产品定位的一部分）。
