# M0 技术验证清单（4 周）

目的：把全项目最大的技术风险前置。菜单栏工具的两个高危环节——**枚举别人的图标**和**替用户拖动图标**——都依赖未公开契约，任何一次系统大版本更新都可能失效。Bartender 5/6 在 macOS Tahoe 上的崩溃（幽灵点击、光标劫持、图标错乱）就是活生生的反例。

M0 的通过标准不是"功能做完了"，而是**知道它在什么条件下会坏、坏了会不会伤人**。

## 前置条件

- 本机 macOS 26.x（Tahoe），带刘海的 MacBook 优先；有条件再借一台非刘海机型。
- 授予辅助功能权限：系统设置 → 隐私与安全性 → 辅助功能。
- 先跑 `swift run tidybar-checks` 确认基线全绿（当前 88 条）。

## 验证项 1：图标枚举可行性（第 1 周）

目标：把 `PlaceholderMenuBarReader` 换成真实现，并确认覆盖率。

1. 在 `Sources/TidyBarCore/Accessibility/` 新增 `AccessibilityMenuBarReader`，用 `AXUIElementCreateSystemWide` + 菜单栏 AX 元素枚举子项，产出 `ManagedItem.Discovery`。
2. 记录并对比以下 App 的图标是否可枚举、title 是否稳定、frame 是否准确：系统时钟/控制中心/电池/Wi-Fi，第三方 Dropbox/微信/Raycast/iStat Menus，以及一个自研 `NSStatusItem`（用 `scripts/fixture-statusitem.sh` 起 6 个测试图标）。
3. 关键判定：
   - 图标 **消失/新增** 时能否在 500ms 内察觉（对应 A7 新图标策略）。
   - 同一 App 改名/切换语言后，`ManagedItem.stableID` 是否仍指向同一图标（这是配置不被抹掉的前提）。
   - 枚举一次的耗时与调用频率上限，用来定节流值。
4. 产出：`docs/findings/01-enumeration.md`，写清哪些 App 读不到、失败模式是什么。

失败退路：若枚举不稳定，隐藏能力退化为"按 owner App 整体收放"，并在 README 明示限制。

## 验证项 2：⌘ 拖拽与事件哨兵（第 2-3 周）

目标：证明"能拖"，更要证明"拖不动时会立刻停手"。

1. 实现 `SyntheticDragMenuBarMover`：`CGEvent` 序列 = 按下 ⌘ → 移动到图标中心 → 按下左键 → 分步移动到目标 X → 松开 → 松开 ⌘。全程经 `EventSentinel` 预检/复核。
2. 逐项做破坏性测试，每项都要看到**中止 + 回滚 + 无残留 pending 意图**：
   - 拖拽中途用户真的按住鼠标（应判定 `.userInteracting`）。
   - 拖拽中途用触控板挪动光标（应判定 `.cursorDrift`）。
   - 目标 App 在此期间退出（应判定 `.itemVanished`）。
   - 连续 50 次快速拖拽（应被节流，不得堆队列）。
   - 在系统更新/重启后（应自动落到 `panelOnlyFallback`，且不损坏用户菜单栏）。
3. 记录副作用：拖动过程中是否短暂抢走焦点、是否触发 Mission Control/调度中心手势、Spotlight 弹出时是否互相干扰。
4. 每次实测都必须写进 `hasConfirmedDragSupport` 的判定流程：**未在同一台机器、同一系统版本上连续 100 次全绿，不得开放完整接管**。
5. 产出：`docs/findings/02-drag.md`，附最短可复现脚本。

## 验证项 3：崩溃与强杀安全（第 3 周）

1. 在拖拽执行中 `kill -9` 进程，重启后确认：图标位置未损坏，`LayoutJournal` 的 pending 被识别并重放（用例 `orphanedIntentIsReplayedOnLaunch` 已在，但需要真机验证真实系统状态）。
2. 关机/注销时进程被终止，再登录：布局一致。
3. 产出：把真机结论补进 `LayoutJournal` 的注释，作为"为什么需要这个文件"的依据。

## 验证项 4：占用与功耗（第 4 周）

1. `./scripts/build-app.sh && ./scripts/perf-check.sh --minutes 60`：静置 1 小时，对照 `PerformanceBudget`（内存 40MB、空闲 CPU 0.1%）。
2. Instruments Allocations 检查是否有位图缓存增长（`ImageCache` 上限 20MB）。
3. 活动监视器 Energy 面板读数记录为"低"；若为"高"，先查是否退化成轮询。
4. 刘海屏上面板与图标是否被遮挡（`PanelGeometryTests` 已覆盖纯几何，需真机对照）。
5. 产出：`docs/findings/03-performance.md` + 一组基线数字（发布时公开）。

## M0 Go / No-Go

全部满足才进 MVP（报告 §6 M1）：

- [ ] 图标枚举在 10 个真实 App 上稳定，且有明确失败清单
- [ ] ⌘ 拖拽 100 次全绿，5 类破坏性测试全部安全中止
- [ ] 强杀恢复在真机验证通过
- [ ] 静置 1 小时：内存 < 40MB、空闲 CPU < 0.1%、Energy 评级"低"

任一不过，按报告 §4.4 走降级路线：**只做收纳面板（不动系统图标），把产品定位收敛为"下拉面板 + 搜索 + 规则"**，并据此重写 MVP 范围——不要在不可靠的机制上继续堆功能。
